01 — The four decisions that define the program

What the scope change actually forces

The earlier research was right for the problem it was given. Three things widened it: controllers went from one to six, the Pi went from the target to the first target, and the DJ software entered scope as a sync source. Each of those invalidates a specific earlier decision, and each is settled below.

Renderer

wgpu everywhere

Vulkan on the Pi and the 3090, Metal on the M2 Pro. One compositor, one shader toolchain. GLES/EGL survives only as a Pi escape hatch, taken by measurement and recorded honestly if taken.

ADR-100
Control model

Virtual surface, named regions

Devices project their physical topology onto abstract regions. Adding a seventh controller becomes a TOML profile, not an engine change. No crate below the binary names a product.

ADR-101
Show portability

Tiers with declared degradation

One show file. It declares what it needs and exactly how to shrink for the Pi. The engine never guesses which of your six layers to drop.

ADR-102
Delivery

Two tracks, shared crates

Track A hardens the Pi rig for your gigs. Track B builds the portable core. The control-surface work is written once and consumed by both — it is the same phase.

The blind spot all four share: every one of them models control input as "the Stream Deck." The closest gets a ControllerAdapter trait, but its feedback type still assumes bitmap keys. None anticipates velocity-palette LEDs, RGB SysEx grids, relative encoders with LED rings, or an OLED strip. That gap is the largest new piece of work in this plan.

Carried forward unchanged: the audio uniform contract and dual-rate EMA smoothing (fast attack, slow release — a single symmetric EMA is the classic mistake and produces exactly the flicker you're avoiding); spectral-flux onset detection against a rolling median + MAD; the rule never to normalise a spectrum by its own maximum, which would make silence look active; the typed-internal / JSON-at-boundaries discipline; and the zero-copy evidence list.

03 — The subsystem the prior research doesn't have

One clip grid, six physical topologies

Six controllers, four input paradigms, five feedback models, three operating systems. Integrating each against the engine directly produces six copies of the paging, banking, soft-takeover and feedback-diffing logic — and a seventh the day you buy another controller. Instead the engine exposes named regions, and each device projects its own scroll window onto them.

Stream Deck XL
USB HID · 4 × 8 · 96px JPEG per key

Clip launch and page navigation. The only device that can put a clip thumbnail on the button.

Launchpad Mini MK3
USB MIDI · 8 × 8 + 16 · RGB, hardware pulse

The primary clip grid. Must be put into Programmer Mode by SysEx on every reconnect, or the note layout is wrong. Use the hardware pulse for a pending quantized launch — one message instead of an animation.

Akai Fire
USB MIDI · 4 × 16 · RGB bulk + OLED

FX parameters, secondary grid, status readout. No official spec — community-reverse-engineered. One SysEx bulk message repaints all 64 pads, which makes it the cheapest device to refresh. Encoders are relative, so no takeover needed.

APC Key 25
USB MIDI · 5 × 8 · mk1 3-colour / mk2 RGB

Note-driven modulation, secondary grid, 8 macro knobs. mk1 and mk2 have materially different LED protocols — detect by product ID, load separate profiles. The 25 keys default to modulation, not launch: a keyboard under your hands mid-set is worth more as expression than as 25 more buttons.

X-Touch Mini
USB MIDI · 8 encoders + 2 × 8 · rings, 2 layers

The mixer surface. Layer opacities on encoders, master on the fader, blend modes on the buttons. Ring display mode encodes parameter type — pan for bipolar, fan for unipolar. Configure it in X-Touch Editor on your PC before it goes near the Pi; the editor doesn't run on Linux and the setting lives on the device.

MPK mini mk3
USB MIDI · 2 × 4 × 2 banks · no addressable feedback

Portable expressive input. Profile it with no feedback capability until proven otherwise, and bind it so nothing needs feedback — momentary actions, not toggles whose state you can't see. Its on-device editor makes it the device most likely to arrive with a different map than the profile expects, which is the strongest argument for MIDI learn.

RGB via SysEx Bitmap key Monochrome LED No feedback Encoder ring

The acceptance test for the whole design: a seventh controller can be added by writing one TOML profile, with Rust code required only if its LED protocol is SysEx bulk. Everything else — paging, banking, takeover, feedback diffing, learn — is already written.

The gotcha that will bite on Windows: WinMM opens a MIDI input port exclusively. If Resolume holds your APC, the engine can't — and vice versa. ALSA and CoreMIDI are both multi-client, so this is the one place your three platforms genuinely disagree about something you'll notice immediately.

04 — Where branching is authorised

Three tiers, one show file

05 — Tempo and phase

Beat-quantized launching needs an authority

The FLX10 in rekordbox or Serato runs in the vendor's native mode, so there's no MIDI wire to take clock from. Both applications speak Ableton Link, which carries tempo and phase over the network — so the Pi joins the Link session over Ethernet and audio analysis becomes the fallback rather than the primary clock. One arbiter owns the answer; everything else reads it.

  • Priority by default: manual tap → Link → MIDI clock → audio, each with a confidence floor. Audio-derived tempo is admitted only above 0.6, because it's an estimate and must never silently outrank an authoritative source.
  • Handover never jumps. BPM ramps over a beat and phase aligns at the next bar boundary of the outgoing source. Losing every source holds the last BPM and decays confidence rather than zeroing it — a BPM-locked effect has to degrade through a breakdown, not stutter.
  • A launch window, not an instant. Press 50 ms after the bar and it still lands on that bar. That forgiveness is what makes hardware feel right.
  • Preroll ahead of the boundary. A quantized trigger cues its decoder slot the moment it's received. A quantized launch that misses its boundary because decode started late is worse than an unquantized one.
06 — Two tracks over a shared middle

Gig-ready first, portable in parallel

Track A — Pi appliance

≈ 24–37 days
A0 hardware bring-up A1 typed core A2 control surfaces · shared A3 two decks A4 freeze & harden

Hardens the existing repository so it runs your gigs. It keeps mpv and takes no new features after A4. A0 exists because every latency and decode claim in the corpus is currently a reasoned budget, never a measurement.

Track B — portable core

≈ 54–82 days
B0 workspace B1 GPU spike · highest risk B2 ISF host B3 decode backends B4 audio + tempo B5 = A2 B6 desktop app B7 Pi port B8 macOS

The clean workspace. Three crates — vocabulary, command plane, control surfaces — are written once and consumed by both tracks, which is what stops the parallelism from being duplicated work. At B7 the portable engine replaces Track A and Track A is retired.

Suggested order for one person: B0 (mostly written already) → A0, because you need to know what's actually true about your Pi → A1 + A2, the block that makes all six controllers work → B1 on the 3090, interleaved with A3 since it's a different machine and a different head-space → A4, then gig with it → B2 through B8 without gig pressure.
